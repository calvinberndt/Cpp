Why Virtual Destructor?

WITHOUT virtual ~Person()
Person* p = new User("Alice", "pwd", 100);
delete p; // Only calls ~Person()
// User::account NEVER deleted!
// MEMORY LEAK!
WITH virtual ~Person()
Person* p = new User("Alice", "pwd", 100);
delete p; // Calls ~User() first
// ~User() → delete account
// ~Person() called automatically
// SAFE! No memory leak.

Memory Management Strategy

Rule of Three implementation and dynamic array growth using exponential doubling strategy.

Rule of Three Implementation

User Class
// 1. Constructor
User(name, pwd, bal) {
account = new BankAccount(bal);
}
// 2. Copy Constructor (DEEP COPY)
User(const User& orig) : Person(orig) {
account = new BankAccount(*orig.account);
}
// 3. Destructor
~User() {
delete account;
}
BankAccount Class
// Copy Constructor
BankAccount(const BankAccount& orig) {
transactionHistory = new Transaction[orig.capacity];
for(i = 0; i < orig.count; i++)
transactionHistory[i] = orig.transactionHistory[i];
}
// Destructor
~BankAccount() {
delete[] transactionHistory;
}

Polymorphism in Action

Runtime polymorphism through virtual functions allows treating User and BankManager uniformly via Person pointers.

Polymorphic Behavior Example

// Store different types in base pointer
Person* people[2];
people[0] = new User("Alice", "pwd", 500);
people[1] = new BankManager("Bob", "admin");
// Same function call, different behavior
for(int i = 0; i < 2; i++) {
people[i]->displayDetails();
// User: shows account info
// Manager: shows management info
}
// Proper cleanup via virtual destructor
for(int i = 0; i < 2; i++) {
delete people[i];
// Calls correct destructor!
}

Virtual Table (vtable)

Runtime Method Resolution
people[0]
User vtable
displayDetails → User::displayDetails()
people[1]
BankManager vtable
displayDetails → BankManager::displayDetails()
Key Insight: The compiler doesn't know at compile time which displayDetails() to call. The vtable lookup happens at runtime.
